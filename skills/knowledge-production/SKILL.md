# 知识作品制作

将用户的想法做成有来源、讲得清、可继续编辑的作品。用户决定想表达什么；AI 承担研究、组织、写作加工与制作。用户只需一句话即可开始，不必先填写完整需求表。

## 默认协作方式

- **观点先来自用户。** 先收集用户的一句话观点、真实困惑、观察或原稿，再做结构和表达。用户暂时说不清时，可提供概念辨析、事实背景和追问，帮助其形成自己的想法；不要先给一套立场让用户认领。
- **形式由用户选。** 未指定形式时，结合内容和受众推荐两三种适合的形式，简述各自用途，让用户选定。已指定形式或已有明确适用的项目约定时，直接沿用。
- **方向不明先停下询问。** 不通过试写整篇、批量生图或先剪一版来替用户选择方向。方向明确后，持续完成已授权的制作，不在每一步重复请求批准。
- **交付实际作品。** 用户要求做到制作时，不能以计划、提示词、脚本代码或素材链接代替目标作品；能力不足时准确报告缺口。

用户若明确只想做中性知识介绍，以其选定的问题和理解目标为方向，不强迫其提出赞成或反对的立场。用户明确改为 AI 自拟观点时可以执行，但仍需澄清主题含义和作品形式，不虚构用户经历。

## 可迁移执行与内置能力

本 skill 使用标准 Markdown 与相对路径，不要求某个 agent、模型、个人记忆或账户。首次使用读取 [references/portability.md](references/portability.md)，确认宿主能读文件、检索资料、运行脚本及操作目标应用中的哪些能力；只检查当前任务需要的能力。没有专门的询问工具时直接在对话中提问并等待。

- **文案去 AI 味**：完整规则已随包附带于 [vendor/text-cleanup/RULES.md](vendor/text-cleanup/RULES.md)，来自 `lieflat-less-ai-tone`。文稿成形后默认执行；无需安装另一个同名 skill。用户禁止改文或尚未到写作阶段时不改写。
- **剪映自动剪辑**：随包附带 `jianying-editor` 的源码运行时和可迁移入口 [scripts/build_jianying.py](scripts/build_jianying.py)。剪辑输入采用相对素材路径的 JSON，不依赖原作者的账户、缓存或素材。视频形式已定而工具未定时优先建议剪映可编辑工程；用户指定其他工具时服从其选择。

进入对应阶段读取 [references/integrations.md](references/integrations.md)。以随包版本为基准，不自动搜索另一台电脑上同名 skill 并换用不同规则。升级外部实现需先核对接口和行为。

基础文字流程只需要能理解这些文件的 agent。在线核查需要搜索/网页访问；剪映建草稿需要 Python、声明的依赖和素材；实际打开、播放或导出需要目标设备的剪映与可用操作能力。缺什么说明什么，不能把文字方案冒充已制作的成品，也不能因设备不同擅自更改作品形式。

## 先恢复上下文

从当前对话、用户指定资料、项目日志、最新稿件及制作记录中，读取与本次任务有关的内容。确认已做选题、已有素材、当前版本和过去确认，避免重复选题、重复下载或推翻已确认内容。

用户本次明确要求优先；本项目的确认高于本 skill 默认。旧记录作为线索，需要核查的时效事实和文件状态重新检查。不同账号、系列和用户的偏好不得互相套用。

既有项目可以带有“只交剪映草稿”“作者只要结构反馈”等约定，按其适用范围执行。广告系列的竖屏、真实动态素材优先、不用概念卡等风格，不自动成为哲学、科普或其他作品的规则。

## 判断何时询问

开始工作前及每次发现新问题时，判断它是否会改变作品的含义、核心观点、形式或重要交付。用下表决定下一步。

| 情况 | 做法 |
|---|---|
| 主题有不同含义，如“二元论”可能指心身问题，也可能指日常的非黑即白思维 | 说明区别并问用户指哪一种；暂停依赖该解释的写作制作 |
| 没有用户观点、问题或理解目标，或无法准确复述其意思 | 请用户用一句话、例子或原稿说明；可做不预设结论的背景调查 |
| 形式未定；不同受众、篇幅或表达尺度会导致明显不同作品 | 提供具体建议和差异，询问当前必须决定的项目 |
| 研究结果反驳核心主张，或需要删改用户明确保留的论点 | 展示证据、影响及可行处理方向，等待用户选择；不迎合错误，也不暗改立场 |
| 核心素材缺失，替代方案会改变论证、视觉风格或完成标准 | 先调查替代方案，再呈现具体取舍供用户决定 |
| 录音含口误、关键听辨不明，或多个版本无法确定最终稿 | 给出原句、精确位置和影响；请用户指定、重录或确认处理方式 |
| 已确认方向内的资料检索、格式整理、可逆排版、常规剪辑及技术修复 | 自主完成；不要求用户选择编码、目录名等普通实现细节 |
| 用户已有明确确认，或同一会话已授权相同步骤 | 复用确认；只有实质变化才重新询问受影响部分 |

询问时说明“哪里不确定—会影响什么—有哪些可选处理”。每次集中一至三个重要问题，选项简短且允许自由回答。不要只问“你有什么要求”，也不要把自己的推测写成用户已确认。

存在方向性未决项时，记录问题并保持等待；未答复、超时或默认选中均不算确认。可继续不依赖该决定的整理和中性查证；用户说“全部先停”时停止所有制作工作。无独立工作可做时，交代已完成内容和等待的问题，结束本轮等待回复，不能凭假设继续下游。

## 从选题到交付

以下是工作推进顺序，不是七次人工审批。已有阶段直接复用；用户只要求选题、查证或局部修改时，完成该范围即可。

### 1. 将一句选题变成可执行方向

理解用户原意，确定作品要解决的一个主要问题及观众最终能理解什么。题目过大时，围绕用户的想法提出可做的小切口和取舍；没有授权时不擅自选定新的核心问题。

形式不明时给出建议，例如：文章便于展开推理，视频适合通过声音和画面讲解，图文适合概念对照。根据实际内容推荐，不固定每次三选一，也不默认做全套多平台版本。

开工所需信息包括主题范围、用户观点或理解目标、面向谁、所选形式和大致体量、必保留内容、期望交付。已有信息直接填入；只有会实质改变作品的缺项需要提问。

### 2. 保存最小工作简报

在作品目录保存简报，记录用户原话与整理后的理解、已确认和待确认事项、素材状态、交付目标。可从 [assets/project-brief.md](assets/project-brief.md) 复制并删减；模板由 AI 填写，不让用户填表。

沿用已有项目结构。新项目在用户指定位置或当前工作区内建立独立作品目录，文件使用明确版本；不把生产稿件写进 skill 目录，不为统一命名移动旧素材或破坏工程路径。

### 3. 研究与证据

读取 [references/research.md](references/research.md)。围绕主要问题核查概念、关键事实、原文语境和有意义的反例。研究用来检验与完善观点，不能只找支持用户的话。

关键说法能追溯到具体来源，区分可核事实、当事人自述、学术解释、争议及本作分析。核心证据不足时先解决，不以流畅文案掩盖缺口。素材链接、已下载文件、可用于正式制作的资产分别记录。

### 4. 结构和文稿

保留用户原始表达，再将观点组织成能被受众理解的顺序。可采用问题—概念—例子—推理—边界，也可用故事、对照、演示等结构；不强套统一开头、热点或升华结尾。

用户给的是口述或草稿时，先忠实转写，标出听不清之处，再整理。用户只要求诊断结构时不代写正文；已要求完整制作时，可围绕已确认观点完成文稿，不能偷换立场、添加虚构的第一人称经历或把 AI 新推断当用户原意。

检查每个主要段落对核心问题的作用，删去仅为显得深刻的概念堆叠。类比要交代边界，人物和原文不能只充当权威装饰。标题、封面和开头承诺的内容必须在正文兑现。

结构需要新增中心判断或改变用户原意时才提问；没有实质分歧时继续制作，不自动追加大纲、初稿、配图等逐层审批。

**成稿清理默认执行。** 文稿结构和事实稳定后，自动按 `lieflat-less-ai-tone` 的白名单处理明确命中的表达，并逐项复查。先保存清理前版本，再生成制作采用版本；未命中文字逐字保留，不改变框架、事实、观点及限定词。没有命中时原样通过，不为证明运行过而制造改动。

去 AI 味在录音、配音、字幕定时和正式排版之前完成。已有录音的实际台词和引用不做去 AI 味改写；字幕忠实对应声音，需要改说法时先请用户确认重录或重新配音。内容后续变化只复查受影响部分及上下文，不全篇反复改写。

### 5. 素材与制作

按所选形式读取 [references/production.md](references/production.md) 中对应部分。先建立内容与表现方式的对应关系：这段文字、画面、声音、图表或操作演示具体说明什么。

剪映分支直接衔接清理后的文稿、最终录音、已核验素材和镜头表，按集成说明完成环境探测、自动建轨、字幕同步、保存与验收；保留独立的口播、原声、BGM 和字幕。默认制作顺序为：用户观点 → 查证与结构 → 文稿 → 去 AI 味 → 最终录音或已授权配音 → 自动剪辑 → 实际检查 → 交付。

真实事件的关键判断用真实证据；抽象知识可用清晰的图解、示意和动画。生成的插画、模拟和重建须保持身份清楚，不伪装为历史照片、实验数据或当事人原话。避免反复用同一素材假装内容推进。

提前确认当前环境能制作和验证目标格式。核心文案与剪映能力使用随包文件；其他格式按宿主已有可用工具实现，列出的专用 skill 只是可选适配，不要求在所有 agent 中安装。缺少工具不自动扩大到安装、付费或更换交付形式；先说明可行方案，涉及作品取舍时询问。

### 6. 按实际交付验收

先验证内容，再检查对应媒体的实际产物，而非只检查生成代码或工程描述。制作任务保留可编辑源文件、必要素材与来源；局部修改只检查受影响内容及衔接，除非发现整体问题。

分开记录：事实核验、文件/工程检查、实际视觉或听觉检查、用户审阅、上传与公开发布。没有实际执行的检查明确写“未验证”。技术通过不能代替用户对观点、风格和听感的接受。

检查通过后交付，只有新修改、失败或未解决问题才扩大检查；不要无限打磨或生成额外版本。

### 7. 交付与继续修改

给出可点击的实际文件或工程入口、版本、已完成事项和少量待定项。短作品可直接在对话中交付；指定应用或文件格式的任务必须交到对应载体。

准确使用“研究完成”“文稿完成”“工程已保存”“已导出”“已上传草稿”“已公开发布”等状态。尚缺核心制作步骤时称阶段性交付，指出下一步，不宣称整件作品完成。

制作本身不默认包含公开发布。用户已经要求上传草稿或发布且目标明确时，完成本轮授权范围，无须再索同一许可；平台、账号或是否公开不明时先澄清。上传草稿不等于公开发布，也不扩展为其他平台同步。

将本次已确认变化、产物路径、检查结果及下一步更新到作品简报。保留原素材和已确认版本，修改另存。用户说“我自己改”“只上传”“不用导出”时，按该边界结束，不继续优化。
